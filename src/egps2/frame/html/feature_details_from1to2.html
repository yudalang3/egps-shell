Detailed features from version 1 to 2:

要解决的科学问题:

毋庸置疑，软件最重要的肯定是其不可替代的功能。所以最好的方式是先自己开发一个计算方法，然后再将其编写成方便实用的软件。
但是开发方法本身费时费力，并且开发一个新方法且验证该方法的有效性并不容易。如何在利用已有工具的层次上，解决软件开发的问题呢？

在实际解决生命科学领域问题的过程中，大部分情况我们对计算方法本身是不怎么关注的。快速组装分析流程其实是最重要的。自从eGPS 1.0版本发布以来，大量用户的使用需求与开发者的软件工程经验被积累。随着计算生物学/生物信息学研究领域的不断发展，以下五类人群组成了eGPS 2.0的目标用户：（1）软件主框架开发与维护人员（2）模块（内置模块与插件）开发人员（3）命令行使用人员（4）图形界面使用人员（5）脚本化生物信息分析人员（这里为JAVA与R用户提供支持，Python用户可使用命令行功能）。新发布的eGPS 2.0版本期望接解决的问题如下：

  1. 如何融合三种主流计算机使用方式：命令行使用、脚本化使用和图形界面使用的优点?
  2. 如何更好地处理软件模块（特别是可视化模块）参数爆炸的问题?
  3. 相较于基于Web server的应用程序，如何更加安全且可重复地进行全流程本地数据分析？
  4. 在有限的时间和精力面前，如何针对eGPS目标用户提供较为合理的处理方案?

一些理论上的设计原则:

  1. 减少用户的认知负载，充分利用GUI软件“自带教程”的特性。 模块有模块的说明与提示，使用户可以快速了解模块的主要功能。
  2. 软件要统筹外观与内涵，既要有现代化软件的界面又要有专业软件所需要的内涵。
  3. 简单好用，通俗地说就是“傻瓜式”，怎么方便怎么来。

实际行动上的变更:

  1. voice数据导入与软件运行机制被设计与实现，该机制融合命令行、脚本化和GUI运行的优点，有效处理开发与使用过程中的参数“爆炸”问题，并支持可重复分析。
  2. 新版本实现了更加美观、更加现代化的图形界面，导航模块借鉴了NCBI数据库的设计，代表性模块界面借鉴了Office ppt的设计。
  3. 软件更新一直是本地单机版软件的痛点，eGPS 2.0实现了增量更新，在有网络的情况下可以实现自动更新。
  4. 主框架内置简介模块，亦可称之为导航模块/ 浏览模块/ 模块锦集，其主要宗旨在于为用户提供一个清晰的导向，以便快速了解并掌握各个模块的核心功能。先从功能、应用领域、复杂性与依赖性角度对模块进行分类。
  5. 主框架为鼓励开发人员编写模块使用教程，新增统一调度使用手册的特性（工具栏的帮助按钮）
  6. 主框架提供模块使用信息统一调用接口，包含模块如何启动、导入了什么数据，用户如何操作软件，以及对结果的解释（工具栏的信息按钮）
  7. 主框架提供模块启动次数与模块特性的统计功能，引导用户解锁模块特性（工具栏的统计按钮）
  8. 主框架提供了多样的提示信息与反馈方式，支持加载svg格式的矢量图标，软件第一次启动时会显示一步一步引导性教程（此特性借鉴自游戏软件教学）
  9. 主框架提供了全局搜索的功能，方便用户快速到达目标模块
  10. 主框架提供了全局设置的功能，通用的图形界面元素如字体、图标大小等可进行设置
  11. 主框架菜单栏新增 Bonus module 选项，这是一个奖励系统，存放一些不影响主要工具的框架功能展示模块，当用户启动软件超过一定的次数即可解锁这些模块（此功能借鉴游戏的设计）。
  12. 主框架菜单栏中的Help选项新增 Report bugs，History, Faq等按钮，执行相应的功能。 底部状态栏新增最新软件版本更新按钮与每日软件使用提示按钮。
  13. 我们对eGPS的目标用户进行了扩充：以下五类人群组成了eGPS 2.0的目标用户：（1）软件主框架开发与维护人员（2）模块（内置模块与插件）开发人员（3）命令行使用人员（4）图形界面使用人员（5）脚本化生物信息分析人员（这里为JAVA与R用户提供支持，Python用户可使用命令行功能）。主框架力争在有限的时间和精力面前平衡各类人员：例如着重开发图形界面模块将会极大地方便第4类人员，但是这样的模块对于第1类人员升级主框架造成了阻碍，对于第2类人员添加功能极其麻烦，对于第3和第5类人员无法使用此模块的特性。

What we abandoned compared with version 1:

1. 工具栏上一些仅在少数模块被使用的按钮以及其中线程控制中的暂停/继续功能

这些无用的按钮指它们仅仅在一两个模块被用到，其余时间大部分处于“不可用状态”。例如：设置字体大小，设置字体Family等。软件eGPS应该是一个多功能的软件平台，理论上应该将所有模块的共性特征提取出来，做成能够“触发”这种共性特征的动作。

上面是一些理论上的设计理由。下面还有一些客观的技术限制：

  1. 我们做的Color选择框，现在暂时无法像Office ppt那样拥有完整的功能，例如显示最近使用的颜色、设置透明度等。故对于功能不全的按钮，应该弃用。
  2. 原来各个按钮以及弹窗在外观上过于老旧，与eGPS 2的设计不符。
  3. 更新工具栏的按钮极其容易产生bug，因为随着模块的是使用，极易造成更新不及时导致状态与实际组件的状态不同。在实现上有两种方式，第一种是从MainFrame得到按钮的实例，第二种是将控制这些按钮的使用逻辑形成若干接口，设计成模块顶层实现的接口。前者极易产生bug，后者开销太大，对于大部分模块而言，它们都不需要这个功能。
  4. 原线程控制中的暂停与继续按钮，不符合实际使用的需求，计算核心代码不会暂停只会取消。并且原来的线程控制涉及到JavaFx和Swing的交互操作，还有各种冗杂了JS的代码，导致调用异常复杂。

2. 历史记录功能

  1. 除了给予VCF文件和MAF文件等计算的需求外，大部分计算几秒内都能完成，暂不需要历史记录功能。
  2. 自从eGPS1上线以来，该功能几乎没有被用到。

3. JavaFx制作的图形界面以及基于Webkit的html与JS代码

这里确切地说是不会再新增功能了，原来的模块功能会逐步替换。JavaFx相对于JAVA Swing设计的思想实在差别太大。两个框架不能直接使用，在实际的项目推进过程中，我们逐渐发现：MVC开发模型对于GUI界面而言过于重型，不如Swing框架将V和C合并比较实用。

还要注意Oracle和OpenJDK本身就将JavaFx从JFC移除，也就是说JavaFx地位同SWT一样，需要作为一个第三方库来使用。为降低软件安装包的大小，我们只用Swing。

JavaFx为后期形成框架，Swing生态系统非常完善，比例可以导出各种矢量图，以及word/ppt/excel等。
